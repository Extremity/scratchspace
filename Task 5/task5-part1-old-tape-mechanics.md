## 3. Tape Capture Mechanism

### 3.1 Eval Callback ([`dflash_eval_callback()`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:1839))

The eval callback is installed on the ggml scheduler and fires for every tensor in the compute graph. It operates in two phases:

**ASK phase (ask=true, [`llama-context.cpp:1846-1881`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:1846)):**
- Returns `true` to intercept hidden state tensors and CPU tape tensors.
- Returns `false` for GPU tape tensors (they're captured by graph-embedded copies).
- The GPU tape bypass is at [`llama-context.cpp:1862-1873`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:1862): when `gpu_tape_fits` is true, tape tensors return `false` from the callback.

**READ phase (ask=false, [`llama-context.cpp:1952-2016`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:1952)):**
- For each tape tensor matched in `tape_name_map`, reads tensor data into the CPU tape buffer.
- The read happens per-layer, per-type (K/V/gate/beta/qkv).
- GPU tape tensors skip the read entirely ([`llama-context.cpp:1971-1974`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:1971)).

### 3.2 What Gets Captured

| Tensor | Shape | Source Graph Node | Purpose |
|--------|-------|-------------------|---------|
| K | `[S_k, H_k, n_tokens]` | `k_conv_predelta-{il}` | GDN key input (after l2_norm) |
| V | `[S_v, H_v, n_tokens]` | `v_conv_predelta-{il}` | GDN value input |
| gate | `[1, H_v, n_tokens]` | `gate-{il}` | GDN gate (pre-exp scaling) |
| beta | `[1, H_v, n_tokens]` | `beta-{il}` | GDN beta (pre-sigmoid) |
| qkv_mixed | `[conv_ch, n_tokens, n_seqs]` | `qkv_mixed_pretranspose-{il}` | Conv state rebuild |

**Directly observed from source:** The captured tensors are intermediates from the DeltaNet forward pass — specifically the pre-delta K, V, gate, and beta values. These are NOT the full layer input; they are the specific values needed to recompute the GDN state update without re-running the full forward pass.

## 4. Replay Mechanism

### 4.1 The Three Replay Paths

The replay system has three paths ranked by preference:

**Path A — Direct GPU GDN Replay** ([`tape_replay_gdn_direct_gpu()`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:3257))
- Requires: GPU tape active, all tensors on same CUDA device.
- Mechanism: Calls `dflash_replay_gdn_state_no_check` CUDA kernel directly via `ggml_backend_reg_get_proc_address` ([`llama-context.cpp:3271`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:3271)).
- Signature: `bool (*)(void *state, const void *k, const void *v, const void *gate, const void *beta, int n_accepted, int S, int H_k, int H_v)`
- Processes all `n_accepted` tokens in one kernel launch per layer.
- Async: launches on CUDA stream, defers sync to `tape_replay_sync()`.
- **No ggml graph involved** — direct CUDA kernel call.

**Path B — GGML Graph Replay** ([`tape_replay()`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:3002) lines 3002-3251)
- Fallback when direct GPU replay unavailable but GPU backend exists.
- Builds a ggml compute graph with GDN ops for all recurrent layers.
- For each layer: creates input tensors (K, V, gate, beta, Q=zeros), builds `ggml_gated_delta_net()` op, extracts state from result, copies back to recurrent memory.
- Executes via `ggml_backend_graph_compute_async()` — async launch.
- State is stored in `dflash_capture->replay_graph_ctx` for deferred sync.

**Path C — CPU Fallback** ([`tape_replay_cpu()`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:4148))
- Used when no GPU backend, partial CPU offload, or multi-GPU target without exact CUDA support.
- Synchronous CPU execution.

### 4.2 CPU Replay — The Core GDN Update Math

The CPU replay at [`llama-context.cpp:4148-4216`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:4148) reveals the exact mathematical operation:

```cpp
// llama-context.cpp:4190-4210
for (int tok = 0; tok < n_accepted; ++tok) {
    for (int64_t hv = 0; hv < H_v; ++hv) {
        const int64_t hk = hv % H_k;
        float g_val = exp2f(tape.gate[tok * H_v + hv] * 1.442695041f);
        float b_val = 1.0f / (1.0f + expf(-tape.beta[tok * H_v + hv]));

        float * S_h = state.data() + hv * S * S;
        const float * k_t = tape.k.data() + tok * (S * H_k) + hk * S;
        const float * v_t = tape.v.data() + tok * (S * H_v) + hv * S;

        // kv = S^T @ k, delta = (v - g*kv) * beta, S = g*S + k⊗delta (fused)
        for (int64_t col = 0; col < S; ++col) {
            float kv = 0.0f;
            for (int64_t row = 0; row < S; ++row) {
                kv += S_h[col * S + row] * k_t[row];
            }
            float delta_col = (v_t[col] - g_val * kv) * b_val;
            for (int64_t row = 0; row < S; ++row) {
                S_h[col * S + row] = g_val * S_h[col * S + row] + k_t[row] * delta_col;
            }
        }
    }
}
```

**Directly observed from source:** The GDN state update per token per head is:

1. `g_val = exp2(gate)` — gate scaling (note: `1.442695041f` is `log2(e)`, converting from natural log to base-2 exp)
2. `b_val = sigmoid(beta)` — beta gating
3. For each column: `kv = S^T @ k` (matrix-vector product: state transpose times key)
4. `delta = (v - g * kv) * b` — delta computation
5. `S_new = g * S + k ⊗ delta` — fused rank-1 update (outer product of k and delta, scaled and added to gated state)

This is a **rank-1 update to the S matrix per head per token**, processing heads sequentially and tokens sequentially. The S matrix is `S×S` per head, and the update is sequential (token t+1 uses the state updated by token t).

### 4.3 Conv State Rebuild

The conv rebuild at [`llama-context.cpp:3877-4032`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:3877) shifts the R (convolutional) state:

```cpp
// llama-context.cpp:3999-4011
for (auto & d : layers) {
    for (int64_t w = 0; w < d.conv_window; ++w) {
        int src_pos = n_accepted + (int)w;
        for (int64_t ch = 0; ch < d.conv_ch; ++ch) {
            float val;
            if (src_pos < (int)d.conv_window) {
                val = d.old_window[ch * d.conv_window + src_pos];
            } else {
                val = d.qkv_mixed[(src_pos - d.conv_window) * d.conv_ch + ch];
            }
            d.new_conv[ch * d.conv_window + w] = val;
        }
    }
}
```

**Directly observed from source:** The conv state R is a ring buffer of size `conv_window` per channel. After accepting `n_accepted` tokens, the ring shifts forward: positions that were beyond the window now use the tape-captured `qkv_mixed` values as new input. The operation is a circular buffer shift, not a mathematical computation.

### 4.4 Async Replay and Sync

Replay is async by design. The sequence is:

1. [`tape_replay()`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:2898) launches GDN replay on GPU (async).
2. Sets `dflash_capture->replay_pending = true` with deferred state.
3. Returns immediately — the server continues with the next draft cycle.
4. Before the next verification decode, [`tape_replay_sync()`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:4034) waits for the async replay to complete.
5. After GDN sync, conv rebuild runs (which may also be async GPU or sync CPU).

The sync point at [`llama-context.cpp:4034-4120`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:4034) uses CUDA events for fine-grained sync when available, falling back to full stream synchronize.

## 5. Answers to 13 Investigation Questions

### Q1: What recurrent state existed immediately before speculative execution?

**Answer:** The pre-draft recurrent state consists of two components stored in the recurrent memory cells:

- **S state** (`s_l[il]`): The DeltaNet/GDN hidden state. Shape: `[n_embd_s]` per layer per cell, where `n_embd_s = S * S * H_v`. Stored as F32.
- **R state** (`r_l[il]`): The convolutional ring buffer. Shape: `[n_embd_r]` per layer per cell, where `n_embd_r = conv_ch * conv_window`. Stored as F32.

**Source:** [`llama-memory-recurrent.cpp`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-memory-recurrent.cpp) defines `s_l` and `r_l` as `std::vector<ggml_tensor *>` indexed by model layer. The backup copies these tensors from the active cell to the backup cell.

**Backup mechanism:** [`dflash_backup_recurrent_state()`](old-versions/beellama.cpp-preview-v0.3.2/tools/server/server-context.cpp:4788) calls `llama_dflash_memory_seq_cp_recurrent_ordered()` or `llama_memory_seq_cp_recurrent()`. This copies the entire R and S state for all recurrent layers from `seq_id` to `seq_backup`.

### Q2: What recurrent state existed after the speculative tokens were processed?

**Answer:** After speculative verification, the recurrent state reflects ALL draft tokens processed (not just accepted ones). The S state has been updated by the GDN forward pass through all `n_draft` tokens, and the R state has been shifted by `n_draft` positions. This state is CORRUPT for the accepted prefix because rejected tokens also modified the recurrent state.

**Source:** The verification decode at [`server-context.cpp:5060-5090`](old-versions/beellama.cpp-preview-v0.3.2/tools/server/server-context.cpp:5060) processes all draft tokens in one `llama_decode()` call. The recurrent state is updated sequentially through all tokens.

### Q3: What information was captured during speculative execution?

**Answer:** Per recurrent layer, per token:
- K (key after l2_norm): `[S_k, H_k]`
- V (value): `[S_v, H_v]`
- gate (pre-exp): `[1, H_v]`
- beta (pre-sigmoid): `[1, H_v]`
- qkv_mixed (for conv): `[conv_ch]`

**Source:** [`dflash_eval_callback()`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:1952) read phase. Tensor names mapped at [`llama-context.cpp:2277-2282`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:2277).

### Q4: Exactly which tensors/intermediates were stored in the tape?

**Answer:** Same as Q3. The tape stores exactly the 5 intermediates listed above, captured from the DeltaNet forward pass graph nodes named `k_conv_predelta-{il}`, `v_conv_predelta-{il}`, `gate-{il}`, `beta-{il}`, and `qkv_mixed_pretranspose-{il}`.

**Critical observation:** The tape does NOT store:
- Full layer inputs (embeddings, residuals)
- Attention outputs
- FFN intermediates
- Logits or probabilities
- Any non-recurrent-layer data

The tape is purely the GDN inputs needed to recompute the recurrent state update.

### Q5: Exactly how those intermediates were later consumed during replay?

**Answer:** During replay, the tape intermediates are consumed as inputs to the GDN operation:

- **K, V, gate, beta** → fed into `ggml_gated_delta_net()` (GPU graph path) or the CPU GDN loop.
- **Q is zeros** — the attention output is discarded; only the state update matters ([`llama-context.cpp:3083-3084`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:3083): "Q: zeros (attention output discarded, only state update matters)").
- **qkv_mixed** → used in conv state rebuild to shift the R ring buffer.

The GDN operation produces `[attn_output | new_state]` as output. The attention output portion is ignored, and only the state portion is written back to recurrent memory ([`llama-context.cpp:3118-3136`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:3118)).

### Q6: Which operations during replay actually modified the recurrent R/S state?

**Answer:** Two operations modify recurrent state:

1. **GDN state update** — modifies S state. In GPU graph path: `ggml_cpy(result_state, s_write)` at [`llama-context.cpp:3135`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:3135). In CPU path: `ggml_backend_tensor_set(s_tensor, state.data(), s_offset, ...)` at [`llama-context.cpp:4214`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:4214). In direct GPU path: `dflash_replay_gdn_state_no_check` kernel writes directly to the state pointer.

2. **Conv rebuild** — modifies R state. In GPU path: `dflash_rebuild_conv_state` kernel. In CPU path: `ggml_backend_tensor_set(r_tensor, d.new_conv.data(), d.r_offset, ...)` at [`llama-context.cpp:4019`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:4019).

### Q7: Which operations were merely bookkeeping or scheduler machinery?

**Answer:** The following are bookkeeping, not state modification:

- `tape_replay_sync()` — waits for async GPU work to complete.
- `dflash_capture->replay_pending = true/false` — tracks async state.
- `ggml_backend_synchronize()` — GPU stream sync.
- Cell position advance: `cells[cell_idx].pos += n_accepted` at [`llama-context.cpp:4031`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:4031).
- Profile counters (`profile_replay_gdn_enqueue_us`, etc.).
- Graph context allocation and tensor view creation.

### Q8: Whether replay performed a full model forward, a partial graph, or only the recurrent DeltaNet/GDN update?

**Answer:** Replay performed **only the recurrent DeltaNet/GDN update**, not a full model forward.

**Source:** The replay graph at [`llama-context.cpp:3002-3251`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:3002) builds exactly one GDN op per recurrent layer. No embedding lookup, no attention (outside GDN), no FFN, no normalization, no output projection. The Q input is zeros because the attention output is discarded.

The comment at [`llama-context.cpp:3082-3083`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:3082) confirms: "Q: zeros (attention output discarded, only state update matters)".

### Q9: Exactly how many recurrent state transitions were performed during replay?

**Answer:** Exactly `n_accepted` recurrent state transitions per recurrent layer.

**Source:** The CPU replay loop at [`llama-context.cpp:4190`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:4190): `for (int tok = 0; tok < n_accepted; ++tok)`. The GPU graph replay creates views of `n_accepted` tokens along the token dimension and feeds them to one GDN op that processes all `n_accepted` tokens sequentially.

Each transition is sequential: token t+1 uses the state updated by token t. The transitions are NOT parallelizable across tokens.

### Q10: How replay handled partial acceptance?

**Answer:** Partial acceptance is the normal case. When `n_accepted < n_draft`:

1. KV cache: trim positions after `n_past_before + n_accepted` ([`llama-context.cpp:4252-4253`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:4252)).
2. Recurrent state: restore from backup (pre-draft state), then replay exactly `n_accepted` tokens.
3. The tape contains `n_draft` tokens of data, but replay only consumes the first `n_accepted`.

**Source:** [`dflash_rollback()`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:4218) receives `n_accepted` as a parameter and passes it to `tape_replay(seq_id, n_accepted)`. The replay functions use `n_accepted` to limit how many tape tokens to consume.

### Q11: How replay handled full acceptance?

**Answer:** When ALL draft tokens are accepted (`n_accepted == n_draft`), NO rollback occurs. The server takes a fast path:

```cpp
// server-context.cpp:7494-7502
if (all_accepted_flat) {
    llama_clear_tree_parent_ids(ctx_tgt);
    auto * mem = llama_get_memory(ctx_tgt);
    if (slot.has_recurrent_only_backup) {
        llama_memory_seq_rm_recurrent(mem, seq_backup, -1, -1);
    } else {
        llama_memory_seq_rm(mem, seq_backup, -1, -1);
    }
    llama_memory_seq_rm(mem, slot.id, slot.prompt.tokens.pos_next(), -1);
}
```

**Source:** [`server-context.cpp:7417`](old-versions/beellama.cpp-preview-v0.3.2/tools/server/server-context.cpp:7417): `const bool all_accepted_flat = (n_accepted_draft == (int) n_draft) && !had_dflash_padding`. When true, no `dflash_rollback()` is called — the backup is simply freed. The recurrent state already reflects all draft tokens (which were all accepted), so no replay is needed.

### Q12: Whether rejected speculative tokens ever needed to be replayed?

**Answer:** **NO.** Rejected tokens are never replayed. Only accepted tokens (the first `n_accepted` of the draft sequence) are replayed. Rejected tokens (positions `n_accepted` through `n_draft-1`) are discarded along with their tape data.

**Source:** `tape_replay(seq_id, n_accepted)` only processes `n_accepted` tokens. The tape data for rejected tokens remains in the buffer but is never consumed. On the next draft cycle, the tape is overwritten with new data.

### Q13: Whether the replay mechanism depended on DDTree, deferred expansion, branch machinery, or tree-specific semantics?

**Answer:** The **core recurrent-state replay is fundamentally linear**. However, the old implementation DID include tree-specific extensions:

- [`dflash_prepare_branch()`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:4294) — uses `tape_replay(seq_id, depth)` to set recurrent state to a specific depth in the tree before verifying a branch.
- [`tree_rollback()`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:5512) — uses tape data to rebuild SSM intermediates for tree-verified tokens.
- `tree_bufs` structure — stores `ssm_intermediates` for tree verification.

**But the fundamental tape replay operation is linear:** it replays `n` tokens sequentially from the tape, updating recurrent state one token at a time. The tree machinery uses the same linear replay as a primitive (replay N tokens to reach depth N, then branch from there).

**Source:** [`dflash_prepare_branch()`](old-versions/beellama.cpp-preview-v0.3.2/src/llama-context.cpp:4294) calls `tape_replay(seq_id, depth)` — replaying `depth` tokens to reach the parent state before verifying the branch. This is the same `tape_replay()` used for flat rollback, just with a different `n_accepted` value.

**Conclusion:** For linear DFlash (no DDTree), tape replay is a pure linear operation: restore pre-draft state, replay N accepted tokens through GDN, shift conv buffer by N. The tree machinery is an orthogonal extension that reuses the same linear replay primitive.

---

## 6. Summary

Old tape replay was a **linear, recurrent-state-only replay mechanism** that:

1. Backed up pre-draft recurrent state (R + S) to a separate cell.
2. Captured 5 intermediates per recurrent layer per token during verification (K, V, gate, beta, qkv_mixed).
3. On partial acceptance: restored backup state, then replayed only accepted tokens through GDN (S update) and conv shift (R update).
4. On full acceptance: no replay needed — backup simply freed.
5. Rejected tokens were never replayed.
6. The replay was NOT a full forward pass — only the GDN state update and conv buffer shift.
7. The operation was fundamentally linear; tree support was an extension using the same primitive.
